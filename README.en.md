# Lineage II C4 NWindow.dll — the C++ source, rebuilt

[Português](README.md) · **English** · [Русский](README.ru.md)

A function-by-function rebuild of the `NWindow.dll` of the Lineage II **Chronicle 4 (Scions of Destiny)** client:
the native UI DLL (windows, controls, NPC HTML, IME, chat, console, messenger, replay). The target is the stock
build of 13/01/2006 (TimeDateStamp `0x43C73652`, Visual C++ .NET 2002 `13.00.9466`, md5
`afab3ae3fa4f85f7f4c323715e5155e3`; 341 classes, 343 exports). The same source builds two ways:

| CMake target | Output | What it is |
|---|---|---|
| `NWindowDecomp` | `build/bin/Release/NWindowDecomp.dll` | **hook mode**: runs next to the stock `NWindow.dll` and replaces every function already rebuilt with a `jmp` to ours |
| `NWindowStandalone` | `build/standalone/Release/NWindow.dll` | **standalone**: the whole `NWindow.dll`, our code only, in place of the stock one |

This is the fourth project of a series (C1 → C2 → C3 → C4): the C3 source, already confirmed in the game, was ported
to C4 by a pipeline of its own (`tools/port`) and completed by hand. The C2 and C3 notes stay in `docs/` because the
method, the tools and much of the data come from them.

## How it works

**Hook mode.** The installer (`tools/install_test.py`) adds an import of `NWindowDecomp.dll` to the stock
`NWindow.dll`. It loads before any stock code runs and puts a `jmp` at the entry of every function we have rebuilt
(an `NW_HOOK_*` next to each definition, `src/re/NwHook.h`). Everything else is still the stock code. Any function
can be switched off in `NWindowDecomp.ini` (`[Hooks] Disable=`) to isolate a bug.

**Standalone (stage 5).** With `NW_HOOK_MODE=0` the hook macros are empty and the source builds `NWindow.dll` on
its own: the 341 `UClass`es (`src/standalone/Classes.gen.cpp`), the globals (`NwGlobals.cpp`), the exports with the
stock ordinals (`src/standalone/NWindow.def`) and the colour cursors (taken from `orig/NWindow.dll` at build time).
The engine (`Core.dll`/`Engine.dll`) loads our DLL as it loaded the stock one.

**GameGuard.** The nProtect GameGuard static library (`NPG*`, third-party code) is **left out** of the standalone:
its entry points are documented no-ops (`include/nwindow/NGameGuard.h`, `src/standalone/NwGameGuard.cpp`). Without
it the C4 login stopped after the `Init` (the login server waits for `AuthGameGuard`); the standalone answers the
query itself, with zeros (`NConsoleWnd::GameGuardQueryX`, `src/nwindow/NConsoleWndC2.cpp`). NKeyCrypt
(`npkcrypt.dll`) is loaded with `LoadLibrary`/`GetProcAddress`.

## Status

- **Hook mode:** **5,456 of 7,202** functions to rebuild are hooked (**93.19 %** of the code bytes). Of the rest,
  587 are convention (scalar deleting destructors, `InternalConstructor`) and 1,038 exist only in the standalone
  (static initialisation, `DllMain`); 121 (34 KB) stay unhooked, nearly all of them the GameGuard library, out of
  scope. Live count: [docs/PROGRESSO.md](docs/PROGRESSO.md) (generated by `tools/build_db.py`). Judges green:
  `hooks: 5456 installed, 0 errors`, `verify_hooks` 0 unexplained, `regcheck` 0 problems, `tools/port/checks.py`
  `CHECKS: ALL OK`, `verify_data` 0 differences. Hook builds of up to 5,387 functions entered the world in the game
  with no exception.
- **Standalone:** links (0 unresolved symbols), passes `verify_standalone.py` (PE, imports, resources, exports,
  classes and vtables equal to the stock ones) and `smoke_standalone.py` (all 9 stages, output identical to the
  stock's), and the emulator differential suite (`tools/port/emu`, Unicorn) runs against it: 127 entries, 35,204
  cases, 0 differences. **In the game the standalone `NWindow.dll` alone logs in, lists the servers and enters the
  world.** The windows opened after that are proved in the emulator; the window-by-window test in the client is
  still partial (`Verificadas no jogo: 0` in the database).
- The technical notes (`docs/`) are in Portuguese (the C4 ones written as guides for agents are in English); code
  comments are in English.

## Requirements

- Windows, **Visual Studio 2022** with C++ for x86 (MSVC v143), **CMake ≥ 3.20**;
- **Python 3** with `pefile` and `capstone` (`pip install pefile capstone`): used by the standalone build (cursor
  extraction) and by every tool; `unicorn` (`pip install unicorn`) for the emulator suite;
- **your own Lineage II C4 client**. No game file is in the repository: copy into `orig/` the files listed in
  [orig/README.md](orig/README.md) (the `NWindow.dll` must have the md5 given there);
- for the judges (`verify_hooks.py`, `regcheck.py`, `verify_standalone.py`, `build_db.py`, `tools/port/*`): the
  Ghidra export in `analysis/ghidra/`, recreated by `tools/ghidra/run_full.sh` (Ghidra 11.3.2 and JDK 21;
  `NWD_GHIDRA_HOME` and `GHIDRA_JAVA_HOME`). It takes a while; run it in the background.

## Build

In a VS 2022 x86 *Developer Command Prompt* (or after `vcvars32.bat`), at the repository root:

```bat
cmake -S . -B build -A Win32 -DNWD_GAME_SOURCES=ON
cmake --build build --config Release
cmake --build build --config Release --target NWindowStandalone
```

`-DNWD_GAME_SOURCES=ON` compiles the game source (`src/nwindow`) in; without it (the default, kept from the first
stage of the port) `NWindowDecomp` is the bare hook runtime and `NWindowStandalone` does not link. The first
`--build` makes the hook-mode DLL and the test tools (`nwd_smoke`, `nwd_difftest`) and needs nothing in `orig/`;
`NWindowStandalone` needs `orig/NWindow.dll` and also writes `NWindow.map` (for `tools/port/map_addr.py`). Warnings
C4244/C4838/C4005 are known (conversions that reproduce the stock code).

## Install and test

Use a **copy** of the client's `system` folder (for example `system_nwtest`), never the one you play from (the
installer refuses a folder named `system`). The commands below read the folder from `--system` or from
`NWD_CLIENT_SYSTEM`:

```bat
xcopy /E /I /Y "C:\...\Lineage II\system" "C:\...\Lineage II\system_nwtest"
set NWD_CLIENT_SYSTEM=C:\...\Lineage II\system_nwtest
```

**Hook mode:**

```bat
python tools\install_test.py
python tools\install_test.py --restore
```

The first writes an `NWindow.dll` rebuilt from `orig/NWindow.dll` with the extra import, `NWindowDecomp.dll` and an
`NWindowDecomp.ini` (the `NWindow.dll` that was there is kept as `NWindow.dll.pre-decomp-bak`); the second puts back
what was there. `NWindowDecomp.log` in that folder lists every installed hook. In the `.ini`: `[Hooks] Enabled=0`
keeps all the stock code; `Disable=` takes an address (`1000cc40`), a method (`NCGDevice::DrawText`) or a class
(`NCGDevice::*`).

**Standalone:** close the game, keep the test folder's `NWindow.dll` aside and copy
`build\standalone\Release\NWindow.dll` over it. Only that file (the client's `npkcrypt.dll` stays there). If the
process faults, the standalone writes `NWindow_crash.log` next to `l2.exe`: `python tools\port\map_addr.py --log
NWindow_crash.log` names the functions. To go back, put the stock file back.

**Cycle** (build, smoke, judges, install, database; stops at the first failing step):

```bat
python tools\cycle.py --game-source --no-install
python tools\cycle.py --game-source --no-install --standalone
tools\port\cycle.bat
```

The second adds the standalone steps (declarations, build, verify, smoke). `tools\port\cycle.bat` calls
`vcvars32.bat` itself and runs the hook-mode cycle followed by the port judges (`verify_data.py`,
`check_breakers.py`, `checks.py`). Without `--no-install` the cycle also installs into the test folder (the game
must be closed). The cycle copies from that folder the DLLs the loader needs (`Core.dll`, `Engine.dll`,
`npkcrypt.dll` and their dependencies) into `build/smoke_system`.

## The judges

"Green" is each one ending with exit code 0; the cycle runs the first four (and the standalone ones with
`--standalone`), `tools\port\cycle.bat` adds the port ones.

| Judge | Command | What it proves |
|---|---|---|
| smoke | `build\smoke\Release\nwd_smoke.exe build\smoke_system` | the patched `NWindow.dll` loads outside the game and every hook reports `ok` (`NWindowDecomp.log`: `hooks: 5456 installed, 5456 registered, 0 errors`) |
| verify | `python tools/verify_hooks.py --log build/smoke_system/NWindowDecomp.log` | each of our functions against the stock one in assembly: bytes popped at `ret`, vtable slots and imports called; a difference is accepted only with a reason in `db/verify_notes.csv` |
| regcheck | `python tools/regcheck.py --game-src` | no stock caller relies on a register our function may change (the stock was built with `/GL`) |
| db | `python tools/build_db.py --game-src` | regenerates `db/functions.csv` and `docs/PROGRESSO.md` |
| verify_data | `python tools/port/verify_data.py` | each function's data constants and displacements match the stock's (`db/verify_data_notes.csv` explains the ones that do not) |
| check_breakers | `python tools/port/check_breakers.py` | no hooked function reaches an `NW_UNPORTED()` (`int3`) |
| checks | `python tools/port/checks.py` | the 15 static checks listed in the file header (return read in `eax`/`st0`, stub `ret N`, stack frames, sizes, constant arguments, CRT, addresses, raw offsets, literals, virtual slots, `vt_audit`, `vt_slots`...): `CHECKS: ALL OK` |
| standalone: declarations | `python tools/verify_standalone.py --checks source` | our `NW_DECLARE_CLASS` / `NW_CHECK_VTABLE` against the stock class table |
| standalone: verify | `python tools/verify_standalone.py --dll build/standalone/Release/NWindow.dll` | PE, imports, resources, exports, classes and vtables equal to the stock ones, without running it |
| standalone: smoke | `python tools/smoke_standalone.py --dll build/standalone/Release/NWindow.dll` | loaded the way the engine loads it: 341 classes registered, `L2Console`/`L2Font` constructed, output equal to the stock's |
| emulator | `python tools/port/emu/run_suite.py --mode hook` / `--mode sa --cases 30 --seed 1` | pieces of the DLL run under Unicorn with the stock code and with ours (hook or standalone) and write the same ([docs/notas/C4_EmuSA.md](docs/notas/C4_EmuSA.md)) |

`tools/difftest.py` (fixed cases against `tests/golden/`) still carries the C1 addresses and refuses to run on the
C4 image; in C4 the differential test is the emulator suite. The cycle does **not** draw the UI: visual changes only
show in an in-game test.

## Layout

```
orig/          your client's binaries (not in git; md5 in orig/README.md)
analysis/      facts from the stock binary (classes, EH, Core/Engine vtables and layouts); analysis/c2/, analysis/c3/ =
               the same data for C2 and C3; analysis/ghidra/ = Ghidra export (generated, not in git)
db/            function database (functions.csv generated) + hand-written names, notes, verifications and port maps;
               db/c1/, db/c2/, db/c3/ = the lists of the earlier projects
include/ue2/   the C4 Core.dll/Engine.dll declarations, checked against the exports (gen/*.vt.inc generated)
include/nwindow/, src/nwindow/    the decompiled source, one class per file
src/re/        hook-mode runtime (hook installer, log, ini, CRT compatibility)
src/standalone/                   IMPLEMENT_CLASS / IMPLEMENT_PACKAGE, globals, NWindow.def, GameGuard no-ops, crash log
tests/         stock reference outputs (golden) and standalone lists
third_party/ue_import/            .def files of the Core/Engine exports (turned into .lib at build time)
tools/         analysis, generation, install, judges, cycle; tools/port/ = the C3 -> C4 pipeline, the port judges and
               the emulator (tools/port/emu); tools/c2/, tools/c3/ = inherited tools (census, packet audit)
docs/          plan, conventions, progress and technical notes
```
